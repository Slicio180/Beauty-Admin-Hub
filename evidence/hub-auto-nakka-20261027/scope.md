# AUD-096 — direct Hub registration to Nakka TEST

Prepared 27 October 2026, Europe/Stockholm. Required owner checkpoint 081f603 / AUD-095. Baseline application AUD-094, 343 tests PASS. Owner requested browser results be collected and recorded in bulk; do not create an evidence-only installer after each following screenshot.

Normal intended workflow: registering an eligible existing player in the Hub sends that player directly to Nakka, without opening the standalone transfer preview. This implementation enables that path only in Beauty — Remote Identity TEST, only for the dedicated t_RqC2_2034 event with its exact TEST title, expected league and pre-start state. It does not enable production, remote/kiosk candidate sync, new league-player creation, multiple events or a date-column migration.

Registration form captures the displayed Hub date when it opens; identity-conflict choices retain it. Transport/bridge allow only the public date field and identity/consent/message fields, then stamp HUB and a private expected date server-side. Registration lock verifies the selected Control date and actual Europe/Berlin submission day, then rechecks immediately before append using the very same real timestamp stored in A. This retains the requested weekly/today workflow, blocks stale/advance-day invisible registrations and never forges a timestamp. Future-event registration remains deferred. Response schema stays A:F, six columns. Remote/kiosk behavior is not routed through the new date helper.

The existing resolver still handles duplicate names, THAT IS ME, different-person details and new players. Only its server-derived existingPlayer:true result is eligible for automatic league matching; client cannot set that flag. A new/different-person player is still saved with normal master/status behavior, but Nakka needs identity review. Existing league identity must be unique by normalized name; duplicate/unknown league identities never create an external entry automatically.

After registration lock release, automatic TEST send reuses the fully guarded transfer preview/save implementation. The registration action authorizes this internal automatic path; manual transfers retain their separate acknowledgement. There is no browser transfer step in the successful registration flow. Preview/save each authenticate and lock, validate fixed target/date/IN status, re-read candidate and prior entries, and use the durable journal and one-use ticket. Automatic path validates preview date and normalized candidate name before confirming it. Existing Nakka entries are reused; existing uncertain markers are inspected using AUD-094 rules and are never erased. No blind API POST retry.

The Sheet registration and external add are not a single cross-service transaction. Once registration commits, a later Nakka failure returns success:true for registration plus a separate ATTENTION result, never false failure for the committed registration. The UI closes the registration form, refreshes the Hub and shows a compact inline outcome naming player/date and Nakka confirmed/attention state. It does not ask the organiser to register that player again. If the whole network response is lost, existing transport asks for reload/inspection, not automatic repetition. Name-conflict protection and durable transfer markers remain in force.

Entry presence proof remains separate from unavailable exact-ID proof. Missing LPID readback returns entryConfirmed:true, identityVerified:false with explanatory text; contradictory ID or incomplete save remains attention/uncertain. The UI result is text-only, clears on logout, and rejects old authentication generations so previous-user results cannot appear after a new login. Session busy-renewal fix and expiry gates are preserved.
