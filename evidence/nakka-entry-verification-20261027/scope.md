# AUD-094 — separate saved-entry proof from league-ID proof

Prepared 27 October 2026, Europe/Stockholm. Required owner baseline 0bf5dfe / AUD-093. Current source baseline AUD-092, 340 tests. No frontend change or automatic-registration-to-Nakka enablement.

Native evidence: Alessio's existing-entry API preview omitted LPID; Adam's preview showed a unique existing league LPID and the correct dedicated TEST target. After a transfer attempt, Adam's retry was blocked. Native Nakka showed both players with League badges and comparison showed 2 matching names, 0 unmatched/duplicates, both IN. This establishes presence and native league association, not exact equality to the previewed LPID. The original Adam save response and exact failure point were not supplied, so the code must not assert the original cause conclusively.

The former readback required LPID to be exposed by the entry API. This update explicitly separates two properties. A successful one-entry POST receipt, exact returned TPID/name, one-entry increase and preservation of every previous projected entry verify the entry. If the new entry's LPID is absent, durable state is ENTRY_VERIFIED_LINK_UNEXPOSED, readbackVerified is true for entry presence, identityVerified is false and the message says the reviewed ID was sent but its saved link is not available for exact-ID verification. A contradictory nonempty LPID still fails uncertain. No receipt, altered prior entries, wrong TPID, malformed data or persistence failure remains uncertain and is never retried.

Existing durable ATTEMPTED records can be inspected read-only. If the candidate is present, event/date/intended name/LPID match the saved marker, count increased by exactly one and removing that candidate reproduces the original entry fingerprint, the preview returns PRESENT_AFTER_ATTEMPT. It reports entry readback separately from identity readback, operationVerified:false, changed:false, no ticket and no new POST. It leaves the original journal byte-identical. This does not retrospectively declare that original network operation successful or resolve its receipt. Missing/changed metadata, prior-entry drift, replacement TPID in a completed journal, malformed marker or missing candidate stays blocked for manual review. Never delete a marker to force another transfer.

All previous fixed target/project/league/title and pre-start gates remain. Existing league identity review and one-use preview remain. No production, Sheet, master/league mutation, deletion, journal-clear feature, rollout or new background registration sync. Only HubTestNakkaTransfer.gs is uploaded to Google TEST after the local installer passes. HubTest.html and BeautyLiveTest.html remain byte-identical to AUD-092.

Automated verification: full test suite/inventory, both builders, reproducible HTML, missing-LPID entry result, read-only legacy journal reconciliation, drift/receipt/identity failure cases and disposable installer rehearsal. Native review: preview Adam once, expect either PRESENT_AFTER_ATTEMPT without any add button or a truthful remaining review-required result if the snapshot differs. No add should be performed for Adam or Alessio. Exact LPID proof and any later fully automatic registration still require separate qualification.

API basis reviewed in the same development session: https://push.n01darts.com/api/v1/n01_api_manual_en.html documents adding league entries with LPID and a TPID/name receipt; its entry retrieval description does not promise an LPID field. The observed native response, not merely this documentation omission, triggered the separate verification states. Do not label identity verified when the field is unavailable.
